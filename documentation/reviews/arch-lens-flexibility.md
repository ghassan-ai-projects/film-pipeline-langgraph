## Findings

### 1. Provider onboarding is a four-table, one-if-chain ritual; alias ids are memorized in three separate files
- **EVIDENCE:** `fp/providers/factory.py:34-44` selects adapter class by string id via if-chain; `:47-56` `_default_models`; `:59-103` `_default_capabilities`; `fp/providers/credentials.py:48-58` `_env_var_for` mapping (with its own alias rows `veo-fast`/`veo-lite`/`veo-3.1-fast`); `fp/providers/pricing.py:27-33` `PROVIDER_PRICING` (its own alias rows).
- **SEVERITY:** HIGH (extensibility)
- **EXTENSION COST TODAY:** new adapter file + 3 edits inside `factory.py` + credentials row + pricing row + yaml = 6 code touches; miss any one and you get silent fallbacks instead of errors (unknown model → `[]`; unknown capability → generic video defaults `factory.py:96-103`; unknown rate → `$0.00` `pricing.py:35,42`).
- **TARGET DESIGN:** one declarative `PROVIDER_CATALOG` (module-level frozen table keyed by canonical id, listing aliases, env var, models, capabilities, pricing entry) consumed by factory/credentials/pricing. Adapter selection stays a class map `{id → class}` next to it. A new real provider = 1 adapter file + 1 catalog row + optional yaml.
- **MIGRATION:** mechanical — move existing literals into the catalog verbatim; keep `build_provider_adapter`, `_env_var_for`, `rate_for` signatures so callers don't change; add a test asserting the three derived views agree on alias sets.
- **EFFORT:** M. **RISK:** low (pure data reshuffle; pricing/credentials already tested).

### 2. Agent identity is spread over four parallel tables, and they have already drifted (orphan ids)
- **EVIDENCE:** `AGENT_CLASS_BY_ID` has **12** ids incl. alias `"visual-dev-agent"` (`agents/impl/registry.py:26`) — but `MVP_AGENTS` registers only **11** contracts and contains no `visual-dev-agent` (`agents/mvp/__init__.py`, 11 `agent_id=` rows); routing to it yields `contract=None → {"status":"agent_not_found"}` (`graph/nodes/_agent.py:93,208-209`). `_AGENT_PROFILE_MAP` (`graph/nodes/_context.py:27-52`) lists **21** ids of which ≥9 name no registered contract (`character-dossier-agent`, `environment-bible-agent`, `prompt-composition-agent`, `config-inference-agent`, `generation-scheduler-agent`, `continuity-ledger-agent`, `kb-curator-agent`, `scene-continuity-validator`, `full-movie-flow-validator`). The existing guard `tests/unit/agents/test_mvp_invariants.py:39-62` checks only forward (contract ⇒ impl/template/profile/mock), never reverse. Side note: `tests/unit/agents/test_impl_registry.py:21-23` "unique keys" assertion is vacuous (dict keys can't repeat) — test theater.
- **SEVERITY:** MEDIUM-HIGH (drift already happened; dormant entries look load-bearing)
- **EXTENSION COST TODAY:** 6-7 places (see matrix); reviewer must mentally diff four tables to know which agent ids are real.
- **TARGET DESIGN:** single `AGENTS` table where each row declares id(s)/aliases, class, contract, model profile, template builder. Or minimally: derive `_AGENT_PROFILE_MAP` default from contract's `default_model_profile` (already validated against `ModelRouter` at register time, `agents/registry.py:78`) and keep the map only for true overrides; delete ghost rows.
- **MIGRATION:** add reverse-direction invariant tests first (every key of `AGENT_CLASS_BY_ID` ∈ MVP_AGENTS ids ∪ documented aliases; every `_AGENT_PROFILE_MAP` key likewise) — they will fail today; then delete/rehome ghosts; then collapse if desired.
- **EFFORT:** S for the invariant tests + cleanup; M for full consolidation. **RISK:** low; deleting ghost rows changes nothing observable.

### 3. Three different registry idioms — and three different duplicate/error policies
- **EVIDENCE:**
  - Literal module dict, eager imports, get-or-None: `agents/impl/registry.py:18-36`.
  - Instance dataclass registry, `ValueError` on dup, validation-on-register: `agents/registry.py:31-40` (AgentRegistry), `validation/registry.py:21-24`, `providers/registry.py:16-20`.
  - Class registry, `ValueError` dup / `KeyError` missing: `mcp/contract.py:80-88`.
  - Module singleton, **lazy** `_load_defaults`, and `register()` **silently overwrites**: `agents/prompt_templates/registry.py:65-67` vs `get_required` raising `KeyError` (:73-81).
  - Plus Pydantic serializable mirrors in `schemas/registries/*.py` (the docstring in `validation/registry.py:1-5` itself apologizes for the duality).
- **SEVERITY:** MEDIUM (cognitive tax; the overwrite policy is a real hazard — re-registering a template hides version mistakes that `ValueError` would catch everywhere else)
- **EXTENSION COST TODAY:** contributor must learn which idiom (and error mode) each subsystem uses; there is no wrong answer a linter catches.
- **TARGET DESIGN:** don't unify mechanically (AGENTS.md forbids abstraction without proven need) — do unify **policy**: (a) all registries raise on duplicate registration except through an explicit `replace=True`; (b) lookup-missing returns None only where callers genuinely branch, else raise. Fix `PromptTemplateRegistry.register` first (S).
- **EFFORT:** S (policy alignment + tests). **RISK:** low.

### 5. Validator extensibility bypasses its own registry; thresholds live in three disagreeing places
- **EVIDENCE:** runtime `ValidatorRegistry` is never instantiated in production (`graph/services.py:61` = `None` forever; only consumer of the class anywhere is its own module). `MVP_VALIDATORS` (15 entries, `validation/validators/__init__.py:11-167`) is read solely by smoke-test counting (`app/smoke.py:38-40`). Actual execution constructs impl validators directly (`graph/subgraphs/qc.py:116-118`, `mcp/tools/validation.py:73-115`). Thresholds: schema default `85/75/**65**` (`schemas/registries/validator_registry.py:17-19`), per-entry literals `85/75/**75**` & `80/70/70` (`validators/__init__.py:19,59…`), **again** hardcoded inside each impl's own entry (`impl/scene_continuity.py:218` etc.), while profiles declare yet another set `pass 85/review 75/block **60**` (`profiles/base.studio.yaml:56-60`) that **nothing reads** (grep: zero consumers of resolved `validation.thresholds` in `src/`).
- **SEVERITY:** HIGH (a configurator who edits `profiles/*.yaml` thresholds changes nothing and gets no warning; the numbers 60/65/75 for "block" coexist)
- **EXTENSION COST TODAY:** 3 places (matrix row) — fine — but the declared mechanism ("validator registry", "thresholds knob") is dead API surface that misleads extenders.
- **TARGET DESIGN:** pick honestly: either (a) populate the runtime registry from `MVP_VALIDATORS` at services-build time and have dispatch resolve through it, or (b) delete `validation/registry.py` + `MVP_VALIDATORS` until needed. For thresholds: single source = the registry entry (impl reads `self.entry.thresholds`, not inline literals); profile `validation.thresholds` becomes either a global override applied at services build or is removed from YAML with a doc note.
- **MIGRATION:** (1) make impl validators use `self.entry.thresholds` (delete inline duplicates); (2) decide profile semantics; (3) add config-contract coverage (Finding 9).
- **EFFORT:** S-M. **RISK:** low; behavior-preserving when numbers match (they mostly do; the 65-vs-75 block delta between schema default and entries is currently unreachable via defaults because every caller passes explicit values).

### 9. Systemic fix for knobs: a config-contract test that fails when a setting has zero consumers
- **PROPOSAL (concrete):** new `tests/unit/config/test_config_contract.py`:
